# 梦想乐园

游乐园经营游戏：铺路、建游乐设施和商店、自己搭过山车轨道，让游客玩得开心还愿意掏钱。纯原创内容。

## 玩法

- **开局**：选一个开局方案（青青草地 / 小山坡 / 度假小镇）和难度，点「开始经营」。
- **建造**：先点「铺路」在草地上铺路，再点「设施」或「商店」选一个建筑，点路边的空地落子。设施只有建在路边、游客能走过去才有人排队。
- **游客**：从南边入口大门进来，沿着路走到设施门口排队，坐完付钱；饿了会去小吃摊、饮料摊，累了会回家。心情、饥饿、钱包每个游客都不一样。
- **过山车**：先去「财务」研究过山车图纸（¥5000），再在「设施」里建站台，然后在「过山车」编辑器里一段一段加轨道（直行、左转、右转、上坡、下坡，每段 ¥300）。轨道回到出发格形成闭环才能运营；下坡提速又刺激，转弯多了会减速。
- **门票**：点「票价」调整（默认 ¥10，上限 ¥50；研究「高级票价」后上限 ¥80）。票价越高收入越多，但游客来得越少。
- **财务**：每天结算维护费；贷款每次最多借 ¥5000、总额上限 ¥20000，月息 5%（每 5 天收一次）；现金跌破 -¥5000 就破产。
- **研究**：财务里花钱解锁海盗船、过山车和高级票价。
- **天气**：每天换一次，晴 / 多云 / 下雨，雨天游客少很多。天气由种子决定，同一个种子同一套天气。
- **存档**：点「存档」存在浏览器本地（`park-save-v1`），下次开局菜单里点「继续上次经营」读档。
- **速度**：点右下角的速度按钮切换暂停 / 1x / 2x / 3x。
- **免费建造**：右上角的开关，点一下开、再点一下关（无敌，建造和研究不花钱），放在设置左边。

## 操作

- 手机：点工具栏选工具，再点地图落子；拖动地图平移，双指缩放；竖屏、横屏都可以。
- 电脑：数字键 1 铺路、2 设施、3 商店、4 拆除、5 过山车、6 财务；空格暂停；Esc 关面板；滚轮缩放，拖动平移。

## 数值在哪改

全部数值在 `js/config.js`：地图大小、造价、设施表、门票上下限、贷款、天气、研究、过山车算法系数。

## 模块说明

- `js/config.js`：数值表。
- `js/game.js`：纯逻辑（`Park` 类 + `traceCoaster` / `coasterStats`），不碰 DOM 和 Three.js，Node 里能直接跑测试。
- `js/render.js`：Three.js 低多边形斜俯视画面（`View` 类），地面、路、建筑、会动的设施、游客小人、镜头平移缩放。
- `js/hud.js`：菜单和界面（`showMenu` / `Hud` 类），工具栏、建造面板、过山车编辑器、财务、票价、存档。
- `js/main.js`：入口，菜单 → 新建乐园 → 画面 → 界面 → 固定步长主循环；`?auto=1&seed=42` 跳过菜单直接开局，`window.__park` 供调试和测试用。

## 优化记录（2026-11-21）

先测再改，结论和 2026-11-15 整理轮一致：没有值得改的逐帧瓶颈。逻辑 tick 在 33ms 步长预算内只有零点零几毫秒，渲染一帧 JS 部分不到 1ms，画质自适应（动态分辨率 + 档位）本来就有。下面是实测基线和改动。

**基线实测数字**（Node + 无头 chrome-headless-shell，swiftshader 软渲染，帧率数字只作相对参考）：

| 项目 | 基线数字 |
| --- | --- |
| 逻辑 tick（空园 120 秒） | 平均 0.003ms/次 |
| 逻辑 tick（自然跑 600 秒，8~12 名游客） | 平均 0.011ms/次 |
| 逻辑 tick（强制注入 60 人满员，队列塞满） | 平均 0.023ms/次（单次跑；多次跑 0.023~0.082ms，共享 VM 抖动大） |
| 浏览器内 tick（60 人，fastForward 60 秒） | 平均 0.159ms/次 |
| BFS 寻路 | 每秒 0.3~1.3 次，单次 0.077ms（1000 次中位数 83.7ms，5 遍 27~126ms） |
| visitorById 调用 | 满员每 tick 21.5 次，每次 0.05 微秒 |
| tileAt | 每次 0.1 微秒 |
| view.update（满员 60 人） | 平均 1.65~2.42ms/帧，其中 renderer.render 1.41~1.55ms（软渲染），JS 更新 0.26~0.87ms |
| HUD update | 平均 0.004~0.008ms/次（0.08 秒节流 + makeMemo，早就 memo 化了） |
| 绘制调用 / 三角形（满员） | 20 次 / 6822 个 |
| 加载到菜单 | 525ms（domContentLoaded 320ms）；JS 共约 110KB，Three.js 约 700KB |
| 点“开始经营”到首帧 | 308~2006ms，无头下 rAF 节流抖动极大，主要是调度等待，不是代码耗时 |
| 地面纹理（900 次 fillRect，一次性） | 平均 1.7ms |
| 存档（60 人） | 约 15.7KB，序列化 0.6~0.8ms；浏览器里 save 1.1ms、load 0.5ms |

**改了什么**（只改了三处实测到的浪费，玩法和数值一个没动）：

1. **BFS 寻路（`game.js` 的 `findPath`）**：队列 `q.shift()` 改成队首指针（shift 每次搬移整个数组，是 O(n)）；路径重建 `unshift` 改成倒序收集再 `reverse()`；父格直接存坐标，不用每步 `split(',').map(Number)`。改后 1000 次寻路 5 遍中位数 65.8ms（基线 83.7ms，约快 21%，单次跑波动 16~126ms）；200 组起终点新旧路径逐字相同。
2. **过山车推演缓存（`game.js` 的 `coasterTrace`）**：原来是 getter，每读一次就重新 trace 一遍（render 每帧都读）；现在站台/段数不变时复用缓存，`coasterAdd` / `coasterUndo` / `coasterClear` / 建站台 / 拆除 / 读档时失效重算。改后读 10000 次 5 遍中位数 1.4~1.9ms（基线 23.3ms，约快 12~17 倍），失效逻辑有测试覆盖（撤销、补段、清空、拆除、读档后状态都正确）。
3. **游客渲染循环（`render.js` 的 `update`）**：60 名游客每帧各调两次 `tileToWorld`（每次分配一个小数组），改成内联算术。改后 JS 更新部分 0.87ms → 0.26ms/帧（样本小，26 帧，仅作参考）；画面外观不变，绘制调用和三角形数不变（20 次 / 6822 个）。

**查过但没改的**：

- `visitorById` 的 `.find()`：满员每 tick 才 21.5 次调用，每次 0.05 微秒，改成直查表省不到 1 微秒/ tick，游客增删还要同步表，不值得。
- `visitors` 数组的 `filter` / `splice`：只在游客进出、排队增减时发生，不是每帧热点；`tick` 里 `[...this.visitors]` 每 tick 拷一份 60 人数组，同样可忽略。
- `instanceColor` 每帧重传：颜色在游客出生时就定死了，理论上可以只在游客集合变时传，但每帧只传 720 字节，省不下来有意义的数字，没改。
- 存档全量 JSON 序列化：60 人才 15.7KB、不到 1ms，而且只在点“存档”时跑一次，没改成增量。
- 地面纹理 900 次 fillRect：一次性 1.7ms，没改。
- 加载：JS 共约 110KB、Three.js 约 700KB，没有构建步骤的前提下没法再压；首帧着色器编译只占首帧的约 18ms（308ms 里到首帧是 326ms那次），不是瓶颈。
- `rebuild()` 全量重建建筑网格：只在建造/拆除/读档时触发，不是每帧，不改。

**基线浏览器测试说明**：2026-11-21 上午有人在基线 8a45a8e 上重跑出 27/29、两项失败（铺路格数、旋转木马建造）。我一共跑了 6 次 `test/park.mjs`：基线（改动前）29/29、29/29；改动后 29/29、27/29；为了确认是不是我的改动引起的，又在未改动的 HEAD 代码（/tmp/park-head-test，从 `git archive HEAD` 解出来）上跑了一次，也是 27/29、同样两项失败。所以这两项失败是基线就有的间歇性问题，与我的改动无关；没有为此改任何玩法代码。

机制已查清：`render.js` 的 `_bind` 里点按要满足 `pointerdown` 到 `pointerup` 间隔 < 350ms 且位移 < 8px，否则当成拖动丢弃。无头 swiftshader 下主线程很慢，实测 9 次轻点的 down→up 间隔是 304~1013ms（位移全是 0，根本没拖动），只有 2 次落在 350ms 内，7 次被丢弃，只铺了 2 格路。真机上轻点的 down→up 是几十毫秒，这个门限没问题；无头下事件投递本身就慢过门限。附带一个细节：铺路列表里第一个点 (10,16) 本来就是入口广场（`isPlaza`），`buildPath` 会正当拒绝，满分 9 次里本来就只有 8 次能铺路，检查 `>= 8` 是卡着上限过的，所以只要漏一次轻点就会失败。
